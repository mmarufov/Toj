# Architecture

How Toj is put together, and the reasons behind the main design decisions. The
[README](../README.md) has the overview.

## Network assumptions

Toj is designed for a 3G worst case: **100-500 kbps, high latency, jitter,
packet loss and sudden disconnects**. Two rules follow from that, and most of
the decisions below apply one of them to a specific subsystem:

1. **Never assume connectivity.** Every operation retries, resumes or degrades,
   and a dropped connection is handled as a normal state.
2. **Keep servers close to users.** Round trips are the main cost on a slow
   link, so the backend should run near the people using it. The endpoint is
   one configuration value (`TOJ_CLOUD_BASE_URL` / `CloudConfig`), so moving
   the backend means changing that value.

## Data model

Toj uses a cloud data model similar to Telegram's. Default chats are stored on
the server, synced across a user's devices, and restored on a new login. They
are **encrypted at rest with server-held keys**, which is what makes sync,
history restore and new-device login possible.

End-to-end encryption by default was considered and not chosen. Multi-device
end-to-end encryption is the hard part, and few users verify end-to-end claims
in practice.

**Secret Chats** will be the opt-in end-to-end mode: libsignal, one device per
chat. The libsignal engine is already in the repository
(`Toj/Core/Crypto/CryptoEngine.swift`); the feature itself is not built yet.

## Client

Swift and SwiftUI on iOS 26, using Liquid Glass. I/O, cryptography and
networking are asynchronous and cancellable, and none of it runs on the main
thread.

### Offline-first

```
User taps send
   │
   ├─► write to encrypted local store ──► UI updates immediately
   │
   └─► enqueue in outbox ──► transport ──► server ──► ack ──► reconcile state
```

The encrypted on-device store is **the UI's source of truth**. Views render
from local data and never wait for a round trip. Sends are optimistic: the
message appears right away, and its delivery state is updated when the server
acknowledges it. On a link where a round trip can take half a second, this is
what keeps the app responsive.

### Generated search tables

The Unicode normalizer tables, test vectors and tokenizer manifest under
`Core/Search/` are generated by `scripts/generate-search-*.py`, which probe the
locked SQLCipher build. CI regenerates them and compares the result, so a pod
update or a manual edit can't leave on-device indexes out of step with the code
that queries them. A shallow checkout fails the build instead of skipping the
check.

## Transport

Standard TLS and WebSocket, with REST under `/v1` and the socket at `/v1/ws`.

Toj has no custom wire protocol. Its traffic looks like ordinary HTTPS, which
makes it harder to single out on networks that filter by protocol, and the
backend can be reached through more than one entry IP.

`BackoffPolicy` handles reconnection, which is expected to happen often.

## Backend

Bun and TypeScript over PostgreSQL, in [`server/`](../server): about 60
modules and 455 test cases. It stores messages, syncs devices, and handles
delivery receipts, presence and fan-out.

### Encryption at rest

`envelope-crypto.ts` implements envelope encryption. Content is sealed under a
per-record data key with AES-GCM, and the data key is wrapped by a per-account
key. Unwrapped keys are cached briefly and zeroed after use. Retiring a key
stops new unwraps first; the deletion pass then waits for the cache to drain,
so it can't race a read that copied the key just before it expired.

### Lookups without plaintext

`blind-index.ts` provides versioned keyed digests, so the server can look up
records without storing the value it searches by. Each use (`phone-lookup`,
`otp-code`, `opaque-token`, `media-digest`, `message-send` and others) has its
own HMAC domain, so a digest made for one purpose can't be used as a lookup for
another. Because the digests are versioned, the index key can be rotated
gradually.

### Migrations

Schema changes use expand/contract, which shows in the file names:
`schema-*-expand.sql` adds, `schema-*-contract.sql` removes, and
`schema-*-concurrent.sql` holds index builds that must not take a lock. Old and
new code can both run against the schema while a deploy is in progress.

### Storage

PostgreSQL is the message store, hosted on Supabase today. Media chunks are
stored encrypted in PostgreSQL instead of object storage, which keeps one fewer
service in the request path.

### Sign-in and one-time codes

Accounts use a phone number verified by a one-time code. Codes can go out over
Telegram (`telegram-otp.ts`), SMS (`infobip-otp.ts`) or WhatsApp
(`whatsapp-otp.ts`). SMS to the target market is expensive and returns no
delivery receipts, so the cheaper channels carry most of the traffic and the
user picks the channel.

## Calls

Built and tested, and turned off in every deployed configuration.

- **1:1:** WebRTC, peer-to-peer when possible. Opus audio; VP8, VP9, AV1 and
  H.264 video with simulcast and adaptive bitrate. Under network or thermal
  pressure, video degrades first and audio keeps priority.
- **Group:** LiveKit SFU with end-to-end frame encryption.
- **Relay:** coturn. `infra/coturn/` is a deployment template; no TURN server is
  deployed yet. CI validates the peer-deny policy in the template.

`server/src/staging-config.ts` throws on startup if a call feature flag is set.
The flags stay off until the release gates recorded in
[docs/releases/](releases/) are met.

## Verification

CI runs four jobs on every pull request:

| Job | What it checks |
| --- | --- |
| `server-tests` | Backend suite against a live PostgreSQL service, including cross-domain envelope writes in both canary and full envelope modes |
| `ios-debug-tests` | Verifies the pinned WebRTC artifact's checksum and attestation, compiles the Release path, checks WebRTC namespace isolation and the privacy manifest, and runs the signed test suite on a simulator |
| `sync-chaos-smoke` | A short run of the Toxiproxy fault-injection harness against the real server, checked for correctness |
| `repository-policy-tests` | Search-table generation; shell, plist and coturn policy; SwiftPM and CocoaPods pins against reviewed revisions; every GitHub Action pinned to a full commit SHA |

Dependencies are pinned: the WebRTC XCFramework is a reproducible build
published as an attested release artifact, LibSignalClient is pinned by tag and
by prebuilt-FFI checksum, and the SwiftPM pins are checked against an expected
list in CI.

## Known gaps

As of the current `main`:

- Nothing has run on a physical device or on a real carrier SIM yet. This is
  the largest remaining risk.
- Push notifications are not provisioned. APNs needs an Apple Developer
  account.
- No TURN server is deployed, so calls could not cross restrictive NATs even if
  they were turned on.
- Secret Chats are not built.
- Scale work (partitioning, connection limits, read replicas, a paid database
  tier) is planned before launch and has not been done yet.
